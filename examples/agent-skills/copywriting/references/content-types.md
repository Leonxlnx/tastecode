# Rules by Content Type

## Website pages

### Homepage

The homepage should quickly answer:

- Who or what is this?
- What does the person or business do?
- Who is it for?
- Where should the visitor go next?

Use one clear H1. Keep the opening copy short enough to understand without scrolling. Avoid a broad brand manifesto unless the user asks for one. Do not add a decorative eyebrow above the H1 when it only repeats the page or brand context.

### Service page

Lead with the service and intended customer. Explain:

1. What is included
2. Who needs it
3. How the process works
4. Relevant proof or qualifications
5. The next step

Use specific service terms. Do not hide the service behind a slogan.

### About or career page

Use first person when the page represents an individual. Keep work history factual. Connect prior experience to current work only when the connection is real and useful.

A strong pattern is:

- Current role
- Relevant background
- Responsibilities
- Selected work
- Skills or industries
- Contact path

### Portfolio and project page

For each project, state:

- What was built
- Who it serves
- The writer's role
- Important functionality
- Technology only when useful
- Verified result, if available

Do not invent performance results. A clear project description is better than a vague success claim.

### Contact page

State what the visitor can ask about and what happens after submission. Keep form labels literal. Explain sensitive-data limits in plain language. Use one primary action and a clear booking alternative when available.

### Pricing page

Preserve approved tiers, prices, feature lists, billing language, and scope notes unless the user explicitly requests changes. Improve supporting copy only when it is in scope. Do not blur what is included.

### Section labels, cards, and collections

- Use the section heading as the primary label.
- Do not add an eyebrow, overline, kicker, or preheader when it repeats the heading.
- Keep a compact label only when it adds necessary metadata, such as status, date, version, category, content type, or a real process step.
- Preserve labels and numbering explicitly requested by the user or locked by the design system.
- Do not number service cards, benefits, projects, principles, testimonials, statistics, or ordinary page sections unless the numbers communicate order, rank, count, or reference.
- Avoid leading-zero decoration such as `01 / Services`, `02 / Projects`, and `03 / Contact`.
- Preserve official identifiers, standards, product codes, and other values in which leading zeroes are meaningful.

### SEO fields

Title:

- Unique to the page
- Names the main topic
- Includes the brand where useful
- Reads naturally in search results

Meta description:

- Accurately summarizes the page
- Uses the main topic naturally
- Gives a reason to visit
- Avoids keyword lists and inflated claims

## Apps and software

### Onboarding

- Explain one task per step.
- Number steps only when they must be completed in order. Use normal integers without decorative leading zeroes.
- Tell the user what information is needed.
- Keep progress labels clear.
- Skip broad welcome language when the next action is obvious.

### Buttons

Use the exact action:

- `Create Account`
- `Add Exercise`
- `Save Workout`
- `Upload File`
- `Send Request`
- `View Invoice`

Avoid unclear labels such as `Continue` when a more specific action fits.

### Empty states

Answer:

- What is missing?
- Is anything wrong?
- What can the user do next?

Example:

> No projects have been added yet. Create a project to start tracking requests and files.

### Error states

State the problem and next step.

Example:

> The file could not be uploaded. Check the file type and try again.

Do not use jokes, blame the user, or hide the recovery action.

### Success states

Confirm the completed action.

Example:

> Your changes were saved.

Add a next step only when it is useful.

### Help and settings

Use the same terms as the interface. Put prerequisites before steps. Keep security and privacy instructions direct. Do not assume a specific device, operating system, input method, or level of technical experience unless the product requires it.

### Accessibility and inclusive interface copy

- Describe actions and states without relying only on color, position, sound, or motion.
- Use labels that remain clear when read by assistive technology.
- Avoid blame, jokes, and idioms in errors or recovery instructions.
- Preserve accessibility labels, required legal notices, and safety text unless they are explicitly in scope.
- Do not assume every user can see, hear, type, drag, hover, or use a pointer.

## Blogs and articles

### Title

Make the topic and value clear. Avoid clickbait and vague curiosity gaps.

### Introduction

Answer the main question or establish the useful context in the first one or two paragraphs. Do not begin with a broad statement about the modern world.

### Body

- Use descriptive H2 and H3 headings.
- Skip eyebrow labels that repeat those headings.
- Keep each section focused on one question.
- Use examples, steps, comparisons, or evidence.
- Use numbered lists for real sequences or rankings, and bullets for unordered points.
- Explain technical terms only when needed.
- Link to authoritative sources when claims depend on them.
- Avoid padding to reach a word count.

### Conclusion

Give the practical takeaway, decision, or next step. Do not repeat the full introduction and every heading. Avoid `In conclusion` unless the format specifically calls for it.

## Case studies

Use a factual structure:

1. Client or internal context
2. Problem
3. Scope
4. Work completed
5. Result
6. Current status or next phase

Separate verified outcomes from observations. Never create a metric because the page feels incomplete without one.

## Emails and announcements

Lead with the reason for the message. Keep context close to the request. Make dates and actions easy to find. Use a human sign-off without turning the message into a campaign.

## Social posts

Keep the opening specific. Use the person's name, milestone, project, or event. Avoid generic celebration language. A short true detail usually adds more warmth than several adjectives.

## Documentation and help content

Answer the task directly. Use numbered steps only for a sequence and bullets for options or unordered information. Use `1`, `2`, and `3` rather than decorative leading zeroes. Include warnings before the step where they matter. Keep labels and commands exact.

## Translation and localization

- Preserve meaning, intent, facts, and required terminology.
- Keep product names, company names, commands, code, URLs, and interface labels unchanged unless the task says otherwise.
- Prefer clear sentences that translate cleanly over idioms, puns, and culture-specific metaphors.
- Follow the locale's date, time, number, currency, capitalization, and punctuation conventions when they are known.
- Do not translate regulated, contractual, or safety language without explicit scope and appropriate review.

## High-stakes and regulated content

For legal, medical, financial, safety, compliance, or regulated product copy:

- Preserve the source language and qualifiers by default.
- Do not simplify away conditions, limitations, warnings, or required disclosures.
- Separate plain-language explanation from the official wording.
- Mark unsupported or unverifiable claims instead of repairing them by invention.
- Recommend subject-matter review when publication depends on professional or regulatory accuracy.
